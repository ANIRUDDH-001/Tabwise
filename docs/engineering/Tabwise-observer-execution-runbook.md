# Observer qualification — one-dispatch owner runbook

This committed procedure is preparation only. The repository ships disabled/BLOCK. Publication, activation and execution each require a separate explicit owner decision for the exact final revision and scope; agents must not perform them under implementation authorization.

1. Confirm independent preparation review and frozen R1 integrity, the exact final published commit SHA, qualification content digest, actor and owner decision reference. Any guarded-code/content-scope change requires only a minimal changed-file independent review. A new activation commit must be bound again; do not treat an older approved SHA as authorization for it.
2. Owner alone publishes/integrates the exact workflow revision onto main. Verify that checkout/setup is clean; the entry refuses before runtime loading if it is not. Do not run NVDA on a development machine. Publish by exact SHA from the feature branch, never by the local branch name (local `main` may be stale and `git push origin main` would publish it):
   1. `git fetch origin`
   2. `git merge-base --is-ancestor origin/main <SHA>` must exit 0 (fast-forward only)
   3. `git push origin <SHA>:refs/heads/main` (no `--force`)
   4. `git push origin feat/TW-01-contracts`
   5. `git ls-remote origin refs/heads/main` must print exactly `<SHA>`.
   The status-only activation commit of step 3 is published the same way, as its own fast-forward.
3. After separate owner approval, configure `scripts/tabwise/qualification-status.json` with enabled=true/verdict=PASS and the exact independent reviewer/ref, owner D-number, actor, sorted `QUALIFICATION_FILES` and recomputed digest. This creates a new final activation revision. Bind its full SHA through the repository variable `TABWISE_OBSERVER_APPROVED_REVISION` only inside the owner script of step 4. No variable, status or credential is activated by preparing this document. A retired decision reference (D-72) is never reused.
4. The owner alone runs `scripts/tabwise/d73-observer-dispatch.ps1 -Revision <full SHA> -OwnerRef <D-n>` in an interactive Windows PowerShell 5.1 session from a clean checkout at that revision, first with `-PreflightOnly` (read-only), then without it. Every check precedes any GitHub write: local HEAD, `git ls-remote origin refs/heads/main` and the GitHub API `main` all equal the revision; clean tree; frozen R1 intact; status/digest/owner reference match; signed-in `gh` user equals the status actor; the variable is absent in the authenticated, complete variable listing; and no observer run on any branch is still pending. Only then does it ask for ONE typed confirmation, `AUTHORIZE AND DISPATCH ONCE <D-n> <SHA>`; anything else exits with no change. It then creates the variable (POST, never overwrites), reads it back, and makes exactly one `workflow_dispatch` (`enable_qualification=true`, matching `owner_approval_ref`). There is no retry or rerun path in the script.
5. **Revoke at observed admission, bounded.** D72 run 40826157539 was skipped with zero steps after the variable was deleted immediately after dispatch; the inferred cause is that GitHub evaluated the job-level `vars` condition after that deletion (INFERENCE — GitHub documentation does not state when `jobs.<id>.if` reads `vars`, and a wrong value would look the same from public data). The script keeps the variable until the one bound run's `qualify` job is observed `in_progress` (or completed with a start time), or until `ExposureSeconds` (default 480) after the create attempt, whichever comes first. The bound run must be the single new run with the exact SHA, `main`, `workflow_dispatch`, attempt 1 and the owner as both actor and triggering actor, and must agree with the run id printed by `gh workflow run` when it prints one. Revocation retries DELETE for up to `RevokeSeconds` and counts only when the authenticated, complete listing (exit 0, `total_count` equal to the returned list) omits the variable; error text such as "Not Found" or HTTP 403/404 never counts as absence. Every native command has a `CommandSeconds` timeout that kills its process tree. Worst-case exposure is `ExposureSeconds + PollSeconds + RevokeSeconds + 5 × CommandSeconds` (defaults: 12 min 10 s); limits can only be shortened. Cleanup always runs, first revocation and then cancellation, and neither depends on evidence storage. It cancels the bound run if not terminal, plus any other new non-terminal run that could pass the gate (`main`, same SHA, `workflow_dispatch`). A new run that could not pass the gate is recorded but not cancelled. Cancellation is asynchronous: it is requested, then the run is polled to terminal for up to `RevokeSeconds`.
   - Exit 0 `PASS`: admitted; run concluded `success`; the artifact `tabwise-observer-<run_id>-1` downloaded and verified (manifest/hash) with `candidate_pass: true`; variable revoked; no other new run.
   - Exit 1 `FAILED`: refused, not admitted, run failed or timed out, evidence missing or invalid, or local evidence storage failed. Variable revoked and nothing of ours left running.
   - Exit 3 `UNRESOLVED`: revocation or cancellation unconfirmed, an ambiguous or additional run, a run identity change (for example attempt 2), or a final run listing unavailable. Follow the printed `MANUAL ACTION`: delete the variable in the repository settings, confirm it is absent, and cancel any listed run.
   A skipped, cancelled, failed or unresolved attempt consumes the decision; do not dispatch again under it.
6. After the run, owner resets qualification status to disabled/BLOCK in a follow-up revision. Keep the full Tabwise worker independently BLOCKED. Evidence is written under `cache/d73/execution/<UTC stamp>/` (or `-EvidenceDirectory`): `events.jsonl` (the `end` event carries the outcome), one numbered `obs-NNNN-<kind>.json` per command or decision (never overwritten), the downloaded `artifact/`, and `hashes.json` (SHA-256 of every other file, written last, its own hash printed to the console; record that hash). Retain the original workflow attempt and every cleanup failure; do not edit or replace historical evidence. The workflow artifact is retained for one day. New experimentation requires a new owner decision.

Limitations of this design, which must accompany authorization:
- One-shot is not guaranteed. While the variable exists, another dispatch by the owner account at this SHA would also pass the gate. The script detects and cancels it, reporting UNRESOLVED, but cannot prevent it, and cancellation does not recall keys already sent.
- The admission timing is INFERENCE and must be confirmed from the next attempt's evidence.
- A run that starts after the exposure deadline is not admitted, which yields FAILED.
- Account Actions minutes, storage and billing headroom are not checked by the script; the owner confirms them before running.
- The orchestration is tested only against local mocked `gh`/`git`/`node` (`test/tabwise-d73-admission.test.mjs`). No hosted behaviour has been exercised.

Operational limits: one ephemeral windows-2025 job; workflow timeout5 minutes; core deadline120 seconds; one guarded captured title-report action (frozen capture may send Control before Insert+T), no journey typing or extra stop-speech action; owned static nonce page only; no model calls, credentials or product user data. The workflow's setup may have machine-wide effects on that ephemeral runner. Artifact cap4MB, fixed journal caps, one-day workflow artifact retention. Archive original evidence before expiration through a separately authorized owner action.

Required configuration is status metadata, approved revision repository variable and explicit manual inputs. Existing read-only GitHub workflow token only; no PAT, Meta/Baseten key or Supabase service key belongs in this job. No configuration has been supplied by this runbook.

Unresolved limitations must accompany authorization: actual hosted foreground/relay IPC timing and clean setup are NOT RUN; relay facts E1–E5 and second-client equivalence are unknown; no positive page acknowledgment for Control/Insert keys; initiated keys cannot be recalled; browser restrictions do not establish whole-VM egress isolation; read-only source plus metadata checks do not establish adversarial filesystem isolation (full hashes detect drift at teardown). Offline unit/timing tests provide no physical-safety or full-worker approval.
